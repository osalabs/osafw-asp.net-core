# OSAFW FPF Library Profile

Use this map when a method could help with a concrete work question, at any task size. [fpf.md](fpf.md) owns source access, the current `USING-FPF.md`, revision pins, bounded reading, attribution, and stopping. This table supplies starting points, not a checklist to run or a complete catalog. A sufficient repository answer needs no external lookup.

The routes apply to public framework work and copied applications. Preserve deliberate application behavior and consult optional app-owned `docs/agents/fpf-app.md` for local domains, examples, exclusions, and preferred patterns. That extension supplements these routes within repository contracts and explicit developer decisions.

## Questions from ordinary and larger tasks

| Current question | Source starting point | Return to repository evidence |
| --- | --- | --- |
| What must this intermediate result make possible, and which connection is still missing? | FPF Core `C.39`, especially `C.39:4.1` | The requested user outcome and the next controller, model, template, test, or reviewer that consumes the result. Reuse an adequate way; otherwise explain or construct the missing conversion, action, or dependency. A source extract or successful subtask alone may leave the receiving work unfinished. |
| The result passes or arrives on time, but what does its recipient actually need, and what made it work? | FPF Core `B.5.PI` | Choose an existing demonstration or handoff with a plausible informative comparison; follow the available result into its use, including workarounds. Continue directly when the use is already supported; no comparison at every occurrence. |
| What explains this reproducible failure, and which observation should come next? | Systems Engineering `SYSE.38` | Compare expected and observed behavior at the route, model, template, or provider boundary. Distinguish plausible causes with a bounded observation; verify the user result and establish earlier side effects before retrying. A known sufficient repair can proceed directly. |
| Does this check distinguish the condition that matters? | Checklist DPF, especially `CHK.6` for criteria/checker qualification | [verification.md](verification.md), actual inputs/configuration and consumer outcomes. Identify what a pass supports; a plausible failing case and legitimate passing case expose a weak proxy. More checklist items do not repair an unobserved condition. |
| Would another investigation, requirement, or workflow step improve the decision enough to justify its burden? | Core `C.11.DUA`; Method Engineering `ME.14` for a comparison of working methods; `SYSE.51` for a reusable effort-allocation rule after repeated uninformative effort or consequential under-allocation | [workflow.md](workflow.md), [verification.md](verification.md), and observed work. Compare a feasible next check or change with continuing on the present basis. Preserve binding checks and permissions. Instruction coherence, routing walkthroughs, and measured task effectiveness are different evidence. |
| Does an unclear request, instruction, or technical passage hide the action or change its meaning? | FPF Core `F.19` for a bounded prose repair | The original words, intended action, referents, and action-changing details. Repair only unclear spans; preserve attribution, conditions, exceptions, and quantities. Keep quoted source text intact and label a paraphrase or interpretation. Clearer prose does not establish truth or authorization; ask only when a material ambiguity remains. |
| Which durable public name expresses the actual contract without creating another near-synonym? | Selected naming guidance from FPF Core `F.18` | [Framework naming](../naming.md), actual callers, result shape, side effects, and domain meaning. Existing names can suffice. Adapt useful distinctions to this codebase; do not import FPF type morphology or require a NameCard for ordinary code. Keep any material naming rationale in the existing review or migration record. |
| Which connection makes this explanation or instruction hard to use? | Explanation Design `EXD.6`; Notational Engineering `NOT.7`; independent Narrativization `NSTD.3` for source-grounded accounts | The recipient's needed inference/action, decisive code/doc links, and the actual wording. Repair missing grounds, an unclear relation, or burdensome lookup. A readable account does not establish causation; retain adequate explanations. |
| Can repeated work be cached or shared without changing the answer? | Computational Thinking (`CMP`), especially `CMP.3` | Cache inputs/lifetime, data revisions, completion, side effects, callers and measured cost. Equal keys must justify reuse for the receiving use. Cheap recomputation may be preferable; a cached value must still supply the requested output. |
| Can a helper, workflow step, or dependency be replaced safely? | FPF Core `B.1.5.RS`; Systems Engineering for larger interfaces/configurations | Actual consumers, timing/order, errors, effects and source-copy contracts. Matching one output does not establish substitution. Compare the whole candidate including adapters, preserve needed variants, and use existing migration rules. |
| A source or requirement changed: which earlier result still holds? | `B.5.RR`; Semantic Integration Engineering `SIE.4` / `SIE.11` for mappings or changed meanings | The changed proposition and actual consumers, including app overrides. Matching field names/types do not prove matching meaning. Repair affected claims/checks and retain justified evidence; a cheap scoped regression can beat dependency tracing. |
| How can interrupted work continue without restarting or trusting a stale summary? | FPF Core `A.15.10` | Current Git/resource state, operative instruction, established versus intended actions, and evidence needed next. Recover only the missing basis and continue; no new checkpoint form or repeated consequential write. |
| Search finds plausible text, but can it supply the needed answer at this edition? | Core `F.1:4.4` for uncertain sources or terminology; Knowledge-Corpus Access Engineering `KCAE.SEARCH`, `KCAE.ASSESS`; `KCAE.CHANGE` when sources or indexes change | The source reader, exact edition, available publication set, and receiving question. Reformulate misses, inspect the necessary context, and preserve source conditions. A profile or summary is a finding aid; return to the original when an omitted distinction matters. |
| A tool or saved fact returned useful material, but the next step repeats work or loses a condition. What is missing? | Knowledge-Corpus Access Engineering `KCAE.DELIVER`; Systems Engineering `SYSE.42`, `SYSE.43`, `SYSE.52` for wider tool/context support | Distinguish stored text, returned text, and what the next reader can use. Preserve needed identities, conditions, continuation, and unresolved effects in existing working material. Reuse sufficient context; otherwise supply the missing passage or accessible source. |
| What problem, acceptance boundary, or viable alternatives should shape a feature? | Problem Structuring and Decision Support (`PSD`) | Requirements, `docs/feature_modules.md`, affected topic docs, and acceptance checks. A proposed screen/table is an option, not proof of the operational need; ask only for material missing choices. |
| Which system, intended use, boundary, interface, or architecture changes? | Systems Engineering (`SYSE`) | [domain.md](domain.md), `docs/adr/`, call paths, and public/source-copy contracts. Recover the framework, app, provider and deployment interfaces actually affected. |
| How should an algorithm, model, or representation preserve the needed result under constraints? | Foundational Thinking Suite Reference, or the known Computational / Mathematical Thinking / Mathematical Modeling / Notational Engineering pattern | Exact implementation, assumptions, output shape, invariants and measured limits. For search/index work, preserve needed matches and continuation. Physical Thinking needs an actual physical question, not a software analogy. |
| Which domain practice or combination is missing? | Closest Engineering or independent DPF; Suite Reference or corpus search when uncertain | Canonical topic owner, application facts and specialist evidence. Search by the needed result; the profile does not exclude other methods. |
| Is a distinction about work, methods, claims, evidence, or decisions unresolved? | FPF Core directly | Current source, canonical docs, ADRs, tests, and developer decisions. A document or reported status does not itself establish truth, authorization, freshness, completion, or a business decision. |

Pattern IDs are locators, not an instruction to apply every listed method. Verify applicability and needed conditions in the selected edition. Publication names and prefixes can evolve: use `Read-Fpf.ps1 -Action List -Revision <full-sha>` and exact search results to recover paths and headings. Follow a connected example only while an intermediate contribution or the receiving result remains unresolved.

## Application and specialist routes

The Engineering Suite also covers operations, administration, financial domain modeling, accounting, finance, governance, strategy, marketing, organizations, communities, assets, maintenance, development opportunities, research, human capability, and embodied practices. Discover their current scope in the Suite Reference when the application question calls for it; do not preload that catalog on coding tasks.

Human Capability Development concerns people learning for later work. Use it for developer education or learning applications when relevant; an agent instruction change belongs with Method Engineering and actual task evidence. Material quality or a fluent AI response does not establish human learning or improved agent performance. Equipment maintenance and embodied/physical methods likewise need their stated domain conditions before transfer.

An application may maintain `docs/agents/fpf-app.md` with domain routes, terminology, source-to-code examples, and exclusions requiring specialist legal, clinical, financial, safety, or organizational evidence. Keep it contributor-safe: no credentials, private paths, production data, or cache state. Instruction-pack upgrades preserve it and app-specific shared-profile adaptations.

Return recommendations to the repository owner of the affected contract. FPF does not create another acceptance path or supply missing application facts, row authorization, request tokens, attachment controls, provider guarantees, or decision authority.
