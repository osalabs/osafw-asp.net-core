## Outcome and accepted contracts

Consolidated the four October 31 Settings summaries into this single record at the developer's request. PR #299 remains unchanged. PR #300 owns the Settings foundation and the follow-up simplification; #301 adds category administration, inline autosave and server transfer; #302 adds cached external database-secret resolution. The initial refactor used the existing stack worktree; local acceptance now runs on the primary checkout of the PR #301 branch. Unrelated work is preserved. The developer explicitly approved the local additive schema update and reversible Settings testing documented below; no external service calls were made.

- Deployment/bootstrap values stay in appsettings; shared defaults stay in FwConfig, application policy/defaults in FwHooks.configure, and feature defaults in application Settings.getDefault, shared by consumers and editors and referencing existing feature constants. SMTP uses port 587/TLS enabled; S3 uses sdk mode by default.
- The abstract FwSettings model owns persistence, credential protection, metadata validation, transfer and the application cache; the concrete Settings model owns app-specific behavior and display globals. There is no separate settings store/protection class, runtime migration command, schema-upgrade guard or legacy compatibility subsystem. Existing applications need the offline migration map before deployment.
- Non-credential read(code) uses getDefault(code), with configured values (including dotted keys) preceding application feature defaults. Explicit empty and inheritance remain distinct. Credential classification uses input metadata, including custom names. Missing/inherited credentials are unconfigured and never inherit config/caller secrets. Credential controls use Keep/Replace/Clear; fresh/additive credential INSERTs use basis=1.
- Database-backed sessions and DPAPI-protected keys remain. Optional session-key persistence allows database-free bootstrap; credential writes use a separate strict provider against the same durable database repository. Unavailable durable storage cannot silently produce stored credentials protected only by transient keys. No file key store or distributed cache is introduced.
- AdminSettings uses numeric row access floors plus RBAC; credentials and transfer require Site Admin. Ordinary inherited-action overrides deny unsupported admin mutations/export. It reuses Users.isSiteAdmin and preserves the public Validate extension point. Import is transactional, re-encrypts on the destination, and has no concurrent-editor conflict machinery or AWS-specific pair validator. Credentials use the standard category row editors. Server AWS authentication ignores saved keys without deleting them.
- Production logging omits submitted values by default; ordinary log_pii/DEBUG development diagnostics remain available. Settings audit data stays value-free and Sentry sensitive-request filtering remains. Local debug logging can expose entered values.
- SQL uses model table identifiers, parameters for runtime constants, and readable indented clauses. Unapplied update files retain necessary old-row metadata conversion and new INSERTs, without redundant repairs to rows they just insert. Canonical readability instructions preserve unbraced single-statement conditionals and blank lines between logical blocks.
- New-application preparation is explicit and scoped; repository heuristics do not authorize database mutation or cleanup. Copied-app migration guidance is offline, application-specific and value-free.

## Globals, initialization and cache

FW.G now deep-clones config() and removes only db and override, which can contain database credentials. No presentation-key whitelist or integration-secret-name filter remains in FW/FwConfig. Custom non-secret configuration stays available to templates and nested dictionaries remain request-local. Credentials belong only in Settings; old credential keys must be removed from every config provider during migration.

Settings.applyGlobals() owns the small display override list and its once-per-request flag. Web and email rendering call it; FW contains neither the list nor a settings load flag. The model copies site name/contact/UI values from the application cache and preserves session theme/mode preferences. Date/time, timezone and language remain available without the database. Failed optional display reads retain configured defaults; operational readers still report storage errors.

The cache stores one ciphertext snapshot per database identity with no timed expiration. First read loads the rows once, then other readers and requests reuse them. Supported writes/imports invalidate the snapshot and dependent menu data; the next read refreshes it. Explicit cache clear, eviction or application restart can also reload it. Direct SQL edits require invalidation or restart. FwCache.setValue(..., expire_seconds: 0) now means no timed expiry; its ordinary one-hour default remains unchanged.

Database initialization lives in the existing models/Dev/DevCli.cs. Both CLI and web entry points use it; CLI no longer constructs a controller. DevConfigure retains its IS_DEV/POST/session-token guards and now calls the shared initializer directly. The CLI retains its empty-database guard. Script order includes settings.sql after schema creation; the initializer clears schema and Settings caches even if a later script fails. No new initialization class or session/CSRF fallback system was added.
