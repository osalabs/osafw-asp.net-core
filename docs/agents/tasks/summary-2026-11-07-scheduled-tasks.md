## Contracts and remaining limits

Apply the provider's `upd2026-11-07-scheduled-tasks.sql` before using the new runtime and stop old workers during rollout. The runner remains opt-in through `isFwCronService`. SQL Server and SQLite are supported; other providers are explicitly unsupported for claims. Existing job handlers can return structured details through `runJobAction`; copied handlers require the adaptation described in `docs/cron.md` and the changelog. End bounds are exclusive.

The developer explicitly chose UTC scheduling storage and removal of the database-local DST guards. `next_run`, `start_date`, and `end_date` become `next_run_utc`, `start_date_utc`, and `end_date_utc` across the DTO, runtime, templates/config, and fresh schemas. Raw due-query datetime parameters also use `_utc`. Execution timestamps were already UTC. Recurrence timezone, viewer-local display, local input validation, and shared framework audit timestamps retain their existing meanings; DB.cs is unchanged.

The additive update creates nullable UTC columns/index and preserves old columns/values without guessing their conversion. Before enabling task editing or any worker, application developers must migrate existing instants using the original database timezone, resolve ambiguous historical values, and adapt copied consumers. Starting before migration would treat null new bounds as unbounded. Earlier registered pending/failed/applied PR updates may retain stale stored SQL and need an application-owned additive upgrade; verify the actual UTC columns/index, not just the update status; rollback requires accounting for later UTC edits. These breaking upgrade responsibilities are recorded in CHANGELOG and docs/cron.md. The initial UTC implementation did not migrate a configured application database; the subsequently authorized local UAT applied the update to an empty scheduled-task table.

Actual route testing exposed a pre-existing dispatcher ordering defect: a wrapped RedirectException was rethrown before redirect handling. The narrow dispatcher fix lets inherited CRUD completion and interactive email return normal redirects. Scheduled report execution additionally rejects a live request context before adopting the rendering user's identity.

Sample preserves its declared sort. Custom report schedules use their SQL-defined order because interactive sort columns are discovered from query results rather than a declared scheduling contract. Monthly day 31 skips shorter months, fixed dates remain fixed, and relative periods remain the report developer's responsibility. Email submission cannot guarantee inbox delivery, and interrupted/uncertain outcomes require operator review.

The browser checks do not constitute a human walkthrough of a copied application's reports, real SMTP, IIS lifetime, branding, or deployment. Those need application-specific validation before activation.
