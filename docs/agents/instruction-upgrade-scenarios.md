# Instruction-Only Upgrade Scenarios

Use during instruction-pack maintenance or an application import. Select optional routing probes or bounded agent execution trials for the changed behavior; these are not application runtime tests. Compare the baseline and candidate against current target facts; record results in the existing task summary.

Use identical scenario inputs and protected invariants for the comparison. Repeat a trivial case after material routing edits. Structural validity, a routing walkthrough, actual independent-role execution, and real-task outcomes are separate evidence; report only what was observed.

| Case | Required decision / positive control | Rejected shortcut |
| --- | --- | --- |
| Routine localized fix | Inspect nearby code and the relevant topic; direct execution, proportional verification, and existing summary/review gates. | Load delegation, every overlay, all history, or FPF solely because they are available. |
| Read-only diagnosis or a meaning-neutral correction | Read relevant evidence or check touched text; no environment setup, automatic summary or review loop. | Initialize resources or run a maintenance process merely to answer. |
| Requested edit with no setup | Make the authorized edit and applicable checks; defer unrequested bootstrap, cache, or knowledge scaffolding. | Treat no setup as read-only, or initialize resources unrelated to the edit. |
| Editing an instruction template | Treat the template's embedded procedures as content; make only the requested artifact changes. | Execute the template's bootstrap or maintenance commands against the working repository. |
| Nested instructions and multiple command roots | Discover the rules and working directory for each touched component; identify areas not inspected. | Apply one component's commands or conventions to every component. |
| Required external evidence is unavailable | Mark the check Blocked and continue independent work; resolve it or obtain explicit acceptance before completion. | Relabel required evidence optional because its prerequisite is external. |
| Named reviewer profile is unavailable | Use a suitable fresh generic independent agent within live constraints; disclose the substitution. | Waive available independent review or change primary settings. |
| Interrupted consequential operation | Establish actual effects and remaining work before retrying; retain still-valid evidence. | Treat a planned action as completed or repeat unknown side effects. |
| FPF is unavailable or uses a legacy cache | Inspect without writes; use a readable pin or leave dependent conclusions open. Writable Ensure owns migration. | Refresh, repair or accept during read-only work. |
| FPF passage or change report is truncated | Continue with the same full pin, selectors or comparison pins and returned cursor. | Treat a preview as complete or silently mix editions. |
| FPF cleanup expires a shared-worktree pin | Report unavailable without substitution; keep checkout adoption unchanged. | Silently use the newest candidate or delete during a read. |
| Workflow improvement appears during a feature task | Capture verified optional learning or propose explicitly scoped maintenance. | Treat the observation as authority to change workflow policy. |
| Useful FPF question during a small task | Read the selected edition's usage guidance and needed method; return to the task with conditions intact. | Ban lookup because the task is small, or refresh/adopt during read-only review. |
| Older runtime or classic Web Site | Discover actual language, build tool, layout, and available APIs; adapt instructions while preserving behavior. | Copy upstream runtime identity, C# conventions, project paths, or build commands as app facts. |
| Root-layout app or newly added test project | Locate current project/test/template paths and repair affected routes. | Trust a generated repo map or a historical no-tests statement over current files. |
| No pack or trustworthy import baseline | Classify each path by explicit two-way comparison and mark the missing baseline; add only needed guidance. | Invent a three-way base, overwrite app files, or fabricate historical summaries. |
| App-owned validator or agent profile | Compare the source delta with local changes; preserve stronger assertions and explicit model/cost constraints. | Use replace metadata as permission to discard custom checks or pin the primary model. |
| Partial import or missing routed file | Follow the upgrade prompt's recovery record, inspect actual state, finish missing steps, and validate before full adoption. | Reset completed work, advance the pack version with an unresolved required component, or suppress a failing safeguard. |
| Security/provider/multi-layer change | Retain row/parent authorization, POST/token, provider-specific, and actual-consumer positive/negative controls; disclose unverified deployed behavior. | Treat an instruction-only import or isolated helper test as runtime/provider acceptance or database authority. |
| Policy under review | Fresh reviewer receives outcome, baseline/candidate, scope, overlays and deterministic evidence; active summary follows the initial verdict. | Let edited instructions weaken the controlling review gate or use the author's narrative as initial evidence. |
| Documentation claim under review | Under the existing review gate, identify a planted unsupported claim or contradiction using source evidence and the intended reader's needs; retain supported content. | Accept fluent prose as evidence, flag supported claims without cause, or require unrelated application tests. |
| Private reference evidence | Use only authorized read-only sources; save requested private notes only after checking the destination is ignored. | Copy private names, paths, source, or business details into public guidance or task summaries. |

Preserve target customizations, local instructions, FPF app routes/adoption, unrelated work, and historical records in every case. Scope and review authority come from the user's request and governing instructions, not from these probes.

## Execution trials

Use disposable synthetic projects when a change needs observed agent behavior. This procedure does not add setup or evaluation to ordinary tasks.

1. Record the baseline and candidate revisions or file hashes, selected tasks, protected invariants, host/tools, OS/shell, network availability, and any assistance. Keep task inputs and conditions comparable; disclose differences and unavailable observations.
2. The evaluator retains expected results and reference solutions. Give the tested agent the task, normal project instructions/files, and live host constraints. Do not supply this evaluation procedure as extra coaching or hide instructions reachable through normal project routing.
3. Exercise the affected case and a small contrasting case. When testing continued work, follow an ordinary task with a small correction and related task; inspect whether existing routes are reused without repeated setup. Include local customizations, nested scopes, or unrelated edits when relevant.
4. Inspect actual commands, resulting artifacts, and side effects against the expectations. For interruption recovery, retain partial state and inspect the resumed work. For review criteria, use both a supported statement and an unsupported claim or contradiction without telling the reviewer which is defective.
5. Report walkthroughs, execution results, and baseline/candidate outcome comparisons separately. A successful trial supports only its exercised conditions. Before broader effectiveness claims, use a further case not used to tune the wording and record delivery, mistakes/rework, and available effort evidence. Stop when evidence covers the scoped claim; keep remaining limits and a concrete reason to revisit it in the existing summary.
