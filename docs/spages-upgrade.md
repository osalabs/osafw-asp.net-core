# Upgrading Spages to the block CMS

Read [Spages CMS](spages.md) for the resulting authoring and publication contracts. Back up and review application-specific routes/templates and direct Spages queries before applying this upgrade to an application database.

1. Merge the source, ParsePage templates, assets, `libman.json`, and package/configuration changes. Restore dependencies and build. Retain custom application layouts and merge their CMS rendering changes deliberately.
2. Review the provider-specific additive update, then apply it through the framework update mechanism or the application's controlled migration process. SQL Server: `osafw-app/App_Data/sql/updates/upd2026-09-05-spages-cms.sql`; SQLite: `osafw-app/App_Data/sql/sqlite/updates/upd2026-09-05-spages-cms.sql`. Never run `fwdatabase.sql` on an existing database; those files are destructive fresh-install schemas.
3. As Site Admin, open Pages and run **Convert existing pages to blocks**. This explicit POST converts every unmigrated row, including inactive/deleted and future-dated content, into versioned block documents. Existing rows cannot be saved or undergo workflow transitions until converted, so premature editing or publication cannot replace their original state. It runs one transaction per row and can resume after interruption, including when only deleted rows remain. Rerunning skips completed rows. Public requests never perform conversion writes.
4. Review converted pages, especially unsupported Markdown, attachment links, custom layouts, and executable customization. Original Markdown/custom fields/audit values are retained in the original revision snapshot; the initial publication preserves its status and date. Supported headings, paragraphs, flat lists, quotes, code, tables, local files/images, and dividers become blocks. Unsupported/reference-dependent structures remain editable Markdown. Existing left/right content determines the matching column layout.
5. Configure the author/publisher levels, public origin, and optional homepage ownership. Review direct SQL/typed/string consumers and custom routes against the effective-publication API. Verify both anonymous and restricted page reads and attachment URLs. Set `SPAGES_ENABLED=false` if the application does not use CMS pages.

The schema adds working-draft/editor fields to `spages`, plus immutable content snapshots in `spages_revisions` and local alias records in `spages_redirects`. SQL Server and SQLite fresh schemas contain the same CMS surfaces. The SQLite additive script relies on the framework update ledger for once-only schema execution; content conversion is independently idempotent. MySQL explicitly skips this update and remains on the legacy CMS; root-script fallback must not apply SQL Server DDL to it.

Conversion preserves unsupported source, but unsafe raw Markdown HTML no longer renders. Site Admin executable customization remains separate. A converted legacy table without a caption or image without suitable alt text must be completed before publishing a new revision. Existing publication snapshots remain readable while their draft is improved.

For content rollback, restore an original or historical snapshot into a new draft, inspect it, and publish. Page and snippet rollback are separate. Do not roll back only the binaries after using the new workflow: legacy raw columns are not an authoritative projection of date-based releases. Database/application rollback requires the application's coordinated backup/recovery procedure.

The optional demo installer is separate from conversion and creates drafts only. It skips existing matching content and does not replace `/`.
